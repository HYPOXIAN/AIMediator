## Handoff at a glance

- **User journey:** install, initialize configuration, check the environment,
  analyze an explicit JSONL file, inspect progress, review source evidence, and
  export Markdown/JSON reports. Resume is an explicit operation.
- **Architecture:** extract the existing Python engine into `src/aimediator`;
  expose it through `argparse` and a console entry point. Keep research scripts
  as compatibility callers of the same services.
- **Delivery boundary:** an installable Linux CLI, offline demo, sample reports,
  operating instructions, and verification records. Collection, a web interface,
  and automatic balance changes are outside V1.
- **Highest-risk work:** portable resources, run identity and recovery,
  evidence-preserving review, and compatibility with existing tests.
- **Current state:** design only; product commands remain unimplemented.
  The design-session offline baseline is 147 passing tests.
- **Next action:** give the next agent
  [the implementation prompt](../archive/cli-coding-agent-prompt.md). It should verify the
  baseline, then implement P0-P4 in section 9 and report each acceptance gate.

Sections 3, 4, 6, 7, and 8 define behavior; section 5 permits module-layout
adjustments that preserve those contracts. The dated baseline below describes
this checkout, not a guarantee about a later checkout.

## 1. Delivery decision

The final product is an installable Python command-line tool named `aimediator`.
It accepts a bounded English/simplified-Chinese SF6 feedback dataset and produces
an evidence-linked sample-feedback report, machine-readable artifacts, and
explicit review queues. Users must be able to install it, run it outside the
repository directory, interrupt/resume analysis, review evidence, and export a
report without knowing the research scripts.

V1 is a complete analysis/review/report workflow. Collection and glossary-index
maintenance remain documented preparation scripts; neither is run implicitly
by analysis. A web interface, interactive chat, recurring scraping, new games,
fine-tuning, automatic model downloads, and automatic balance-patch generation
are outside V1. The existing engineering-design preparation script remains an
advanced research tool, with all its prerequisites intact.

The release contains:

1. A wheel and source distribution, a console entry point, and `python -m aimediator`.
2. The command contract in section 4 and packaged prompts, policies, glossary,
   topic anchors, and redistributable synthetic demonstration fixtures.
3. An offline demonstration that exercises the actual pipeline with fixture
   transports, and an example Markdown/JSON report generated by that demo.
4. Installation, configuration, source-review, recovery, and troubleshooting instructions.
5. Recorded offline checks and separately labeled live diagnostic results, if run.

Engineering delivery and independently validated semantic quality are separate
release facts. Missing human labels must not prevent finishing the engineering
workflow, and engineering tests must not be reported as model accuracy.

## 3. Product invariants

1. Preserve original text, immutable IDs, and exact Unicode code-point offsets.
   No translation, emotional-language removal, or model rewriting replaces evidence.
2. Retrieval similarity and alias inclusion do not prove identity, factual
   correctness, historical applicability, or source support.
3. Preserve `buff`, `nerf`, `keep`, and `unclear`; an objection to a nerf is not
   automatically a request for a buff. Preserve conditions and opposing views.
4. Count distinct comment IDs within a group, never independent players. A
   comment can appear in several groups; those counts are not additive.
5. Emotional intensity does not increase or decrease evidence weight. General
   opinions cannot become specific move or numerical proposals.
6. Quality enforcement supplements existing source, identity, numeric-intent,
   semantic-audit, and version-data checks. Review acceptance cannot bypass them.
7. Distinguish raw generation, automatic acceptance, agent review, and human
   review. Source review is not verification of game mechanics.
8. Preserve historical inputs, prompts, frozen labels/splits, decisions, and
   reports. A refactor must not silently resume a historical run under new code.

Default report scope is `collection_sample`, with observed source-date ranges
and unknown patch applicability displayed. V1 does not offer a patch-specific
conclusion mode. The glossary may retain its target-patch identity as reference
metadata, without turning all comments into verified evidence about that patch.

## 4. Public command contract

All commands and options below are target interfaces, not commands available
in the repository today. Help text and documentation use English, consistent
with the repository convention; original Chinese evidence remains Chinese.
Use standard-library `argparse`; a terminal styling framework is unnecessary.

### 4.1 Configuration and preflight

```sh
aimediator --version
aimediator --help
aimediator init --out ./aimediator.json
aimediator doctor --config ./aimediator.json --input ./feedback.jsonl
aimediator doctor --config ./aimediator.json --input ./feedback.jsonl --offline
```

`init` writes a documented JSON configuration template, refuses replacement of
an existing file, and makes no network/model calls. There is no implicit global
configuration discovery. Use packaged defaults when `--config` is absent.

`doctor` validates dependencies, input/schema, resource availability, configuration,
and output capability when an output path is provided. Online mode checks the
configured service, installed model names/digests, and a bounded embedding probe
for the selected provider; no chat generation, downloads, or model substitution.
Offline mode makes zero network calls and marks service/model checks as
`not_checked`. The same validation service is called by `analyze` before creating
a run. Invalid local input/configuration must fail before even a service probe.
Optional `doctor --out PATH` checks a prospective run path and its parent
without creating that run or modifying an existing output directory.

### 4.2 Analysis and resume

```sh
aimediator analyze --input ./feedback.jsonl --out ./runs/sample-001 \
  --config ./aimediator.json --evidence-quality shadow

aimediator analyze --input ./feedback.jsonl --out ./runs/quality-001 \
  --config ./aimediator.json --evidence-quality shadow --stop-after quality

aimediator analyze --resume ./runs/sample-001
aimediator status --run ./runs/sample-001
```

Required for a new analysis: `--input` and `--out`. Optional overrides:
`--config`, `--evidence-quality off|shadow|enforce`,
`--stop-after relevance|quality|full`, `--embedding-provider ollama|configured`,
`--embedding-model`, `--env-file`, `--base-url`, `--num-gpu`, and
`--max-parallel-requests` (section 6).
Language routing stays in configuration, retaining the existing bilingual defaults.
Do not add arbitrary model selection or prompt tuning as part of packaging.

Default quality mode is `off`, preserving current semantics; examples recommend
`shadow` while independent quality validation is outstanding. `--stop-after`
defaults to `full`. Relevance-only requires quality=off; stopping after quality
requires shadow/enforce. Reject invalid combinations before model calls.

A new run requires an absent output path; do not overwrite or infer resume from
an existing folder. `--resume PATH` is mutually exclusive with input/output,
configuration, and semantic/runtime overrides. Output controls (`--json`,
`--quiet`) and credential-only `--env-file` are allowed. It loads the saved resolved
configuration and source snapshot, validates code/resource/model identities,
and continues only compatible work. It need not access the original input path
if the immutable source snapshot and original-byte hash are preserved. A
completed compatible run returns its existing result without repeating calls.

For a configured embedding service, the saved endpoint and model remain frozen
on resume. Obtain its credential from the recorded environment-variable name
or an explicitly supplied `--env-file`; never persist the credential or silently
reopen the original env file. A replacement credential is not a semantic
override. Ignore endpoint/model entries in a resume credential file and clearly
report that saved nonsecret configuration remains authoritative. Missing
credentials for required work produce exit 3 before mutation. The same
`--embedding-model` override rules apply to both providers; do not silently
replace an explicit CLI choice with a value from an env file.

`status` is read-only and offline. It reads saved state and coverage, including
partial runs; it never treats an existing directory as proof of completion.

### 4.3 Source review and report export

```sh
aimediator review export --run ./runs/sample-001 --out ./reviews/sample-001
# Edit decisions.json in the exported directory.
aimediator review import --run ./runs/sample-001 \
  --decisions ./reviews/sample-001/decisions.json --out ./reviews/applied-001

aimediator report --run ./runs/sample-001 --out ./exports/automatic-001
aimediator report --run ./runs/sample-001 --review ./reviews/applied-001 \
  --out ./exports/reviewed-001
```

Review export writes `decisions.json`, `worksheet.csv`, and instructions. JSON
is the authoritative import format; CSV is a readable worksheet only. Export
all structurally complete proposals, including quarantined ones, and preserve
their automatic errors/audit state. Malformed responses without a valid complete
proposal remain failure diagnostics, not editable claims invented by export.

The decision envelope includes schema version, run/source fingerprints,
`reviewer_type` (`agent|human`), reviewer identifier, and a decision keyed by
claim ID with `proposal_sha256`. Each decision requires `accept|reject|uncertain`
and a reason. Export initializes each to `uncertain` with `pending_review`;
exporting or importing an untouched template never accepts evidence. V1 requires
exact coverage of the exported proposal set, matching the current validator;
unfinished records explicitly remain uncertain rather than being omitted.
Reviewer metadata starts unset and must be completed before import. Never
prelabel agent work as human review. Demo documentation uses an agent reviewer
and retains synthetic execution provenance.

Import checks source/proposal hashes and existing grounding/quality rules before
writing a new derived review directory. It never alters raw run files. Preserve
the original proposal and every correction. Reuse existing allowed corrections
(`evidence_ids`, `target`, `recommendation`, `corrected_direction`); identities,
source text, and quality eligibility cannot be edited into existence.

Changed claims lose their prior semantic audit. Import makes no model calls;
such claims remain `pending_reaudit` and outside the enforced audited-mechanism
group. They can be shown in a labeled review appendix. Unchanged quarantined
claims also retain their original automatic failures. A reviewer decision is
an overlay, not a way to fabricate automatic audit success. A later explicit
revalidation workflow is outside V1.

`report` is deterministic and offline. It produces Markdown and JSON together,
using either the automatic view or an explicitly selected compatible review
overlay. It must show which view and reviewer provenance it uses. Review and
export paths must be new and must not be inside or contain the source run;
analysis is the only operation allowed to update active run state.

### 4.4 Evaluation and offline demo

```sh
aimediator evaluate quality --labels ./annotation-template.json \
  --run ./runs/sample-001 --out ./evaluations/quality-001
aimediator demo --out ./runs/demo-001
```

`evaluate quality` wraps the existing quality scorer with explicit label and run
paths. It checks source identity, label schema, point matches, provenance, and
split boundaries. Quality=off has no quality predictions and is rejected for
this command. Label preparation and frozen-silver retrieval evaluation remain
research scripts in V1; do not turn the latter into a generic accuracy command.
No valid denominator means a null metric, never 100 percent. Preserve human,
agent-silver, synthetic, development/test, and conditional/end-to-end distinctions.

`demo` needs neither credentials nor installed models nor network access. It
uses packaged authored bilingual fixtures and injected fixture transports to
run all three quality modes through the actual pipeline, then generates an
enforce example report and review template. All artifacts identify their mock
origin, and semantic accuracy is null. This is also the wheel acceptance path.

### Legacy run support boundary

New analysis/resume uses only `aimediator-run-v1`. For report and review,
provide explicit read-only adapters for current engine reports with
`report_schema_version` equal to `balance-evidence-v2` (off/shadow) or
`balance-report-v3` (enforce), requiring compatible source, relevance, claim,
and mode-specific quality artifacts. Validate the quality mode independently;
a schema name alone does not prove eligibility or source binding passed.
An adapter may derive fingerprints from saved files, but must label provenance
as legacy and must not invent missing model identities, patch verification,
or audit success. Missing required evidence or an unknown schema returns exit 2
with a specific reason. Older experiments remain accessible through existing
research scripts; V1 does not promise general historical-run migration.

### 4.5 Output and exit behavior

Support `--json` and `--quiet` consistently on operational leaf commands.
Structured mode emits exactly one JSON result to stdout; progress goes to
stderr. `--quiet` suppresses routine progress, not errors. Use stable keys
`command`, `status`, `artifacts`, `counts`, `warnings`, `error_code`, and
`error_message`. Help/version keep normal argparse output. Avoid printing raw
model responses, source text, or credentials in routine progress.

The structured envelope applies to errors as well as successes, including
argument validation when `--json` is supplied on a recognized leaf command.
`artifacts` contains named paths and `counts` contains explicitly named units;
use an empty object when unavailable. `warnings` is always a list;
`error_code` and `error_message` are null on success. Keep process exit codes
and machine-readable error codes consistent. Test a failing command in
structured mode as well as successful commands.

Progress names the stage and completed/total comments or claims. Do not show a
percentage of the whole run or an ETA when the remaining number of calls is unknown.

Exit codes:

- `0`: requested work finished and outputs are internally consistent. Normal
  relevance rejection, quality routing, quarantine, and pending source review
  are domain outcomes and do not themselves change this code.
- `1`: unexpected internal error; persist a safe diagnostic if a run exists.
- `2`: invalid arguments, input, configuration, or unsupported schema.
- `3`: service, dependency, or required model unavailable before processing.
- `4`: incompatible resume, fingerprint mismatch, existing output, or writer lock conflict.
- `5`: artifacts saved but requested processing is partial because technical
  failures remain, including exhausted quality/relevance/extraction/audit calls.
- `130`: user interruption; preserve completed work and partial response logs.

Use `run_state` separately from `has_pending_review` and `has_failures`.
For example, fully processed but quarantined claims can finish with exit 0;
valid quality=review is different from an exhausted annotation request.
Offline doctor can exit 0 with online checks explicitly unperformed.

### 4.6 Required offline acceptance walkthrough

After installation, this is the intended complete sequence from a directory
outside the checkout. The demo creates child run directories named `off`,
`shadow`, and `enforce`, each with the normal run contract, plus clearly labeled
demo metadata. Its automatic example report is stored under `example-report/`.

```sh
aimediator init --out ./aimediator.json
aimediator doctor --config ./aimediator.json --offline
aimediator demo --out ./demo-001
aimediator status --run ./demo-001/enforce --json
aimediator review export --run ./demo-001/enforce --out ./review-template-001
# Fill reviewer metadata; leave uninspected decisions uncertain.
aimediator review import --run ./demo-001/enforce \
  --decisions ./review-template-001/decisions.json --out ./review-applied-001
aimediator report --run ./demo-001/enforce --review ./review-applied-001 \
  --out ./report-001
```

An all-uncertain review produces an empty accepted-review view with pending
items visible. The automatic view is still available by omitting `--review`.
This is expected behavior, not a failed analysis or an excuse to auto-accept.

## 5. Package architecture and migration

Use Python >=3.9, preserving the current documented minimum. Use JSON rather
than requiring a newer Python TOML parser. Add `pyproject.toml` with setuptools,
one declared runtime dependency (`numpy`, with bounds validated on supported
Python versions), and `[project.scripts] aimediator = "aimediator.cli:main"`.
Record the exact Python, NumPy, package version, and code/resource hashes per
experiment; a package version range is not an experiment lockfile. Build a wheel
and sdist and record the tested dependency versions in the release validation.

Layout of the package on 2026-11-04, at the end of the code restructuring,
with the modules the pipeline upgrade has added since (`measurement`, step
U0.2), grouped by layer from top to bottom:

```text

  __main__.py              # python3 -m aimediator: calls cli.main
  # interfaces
  cli.py                   # parsing, rendering, exit translation
  presentation.py          # business-only output of the demonstration launcher
  # services
  operations.py            # preflight, doctor, analyze, status
  review.py                # read-only run adapters, review export/import, overlays
  legacy_review.py         # source review of research runs
  reporting.py             # deterministic automatic/reviewed report exports
  evaluation.py            # quality scoring adapter for CLI runs
  quality_scoring.py       # annotation preparation and quality scoring
  demo.py                  # offline demo through the real pipeline boundaries
  engine.py                # legacy research runner
  # orchestration
  pipeline.py              # analysis stages over one RunState
  # infrastructure
  inference.py             # Ollama HTTP calls and the production Transport
  cache.py                 # shared response and embedding cache across runs
  runner.py                # content-addressed journal of model requests
  retrieval.py             # embedding retrieval against the topic anchors
  run_store.py             # identity, snapshots, locking, lifecycle state
  fixture_transport.py     # authored fixture transport of the demo
  # domain
  evidence.py              # source units, numeric tokens, characters, grounding
  evidence_quality.py      # span validation, v2 conversion and information-point routing
  stages.py                # per-stage request data, options, schemas, normalization
  # foundation
  common.py                # strict JSON, canonical bytes, hashing, atomic writes
  schema.py                # JSON-schema builders, constants and validator
  resources.py             # packaged assets, prompts, workspace root
  config.py                # strict JSON config, override resolution, redaction
  balance_policy.py        # identity, retrieval triage and numeric rules
  glossary_vectors.py      # glossary vector index
  # research, outside the CLI path
  design_briefs.py         # engineering-brief readiness
  diagnostics.py           # shared live extract, ground and audit loop
  measurement.py           # request metrics, claim outcomes, evaluation inputs, position scores
  collection/              # collectors and screening: client, store, sources,
                           #   export, screening, balanced, expansion
  assets/
    prompts/               # active paired prompts and quality appendices
    configs/               # routing and policies
    data/
      glossary.json        # bilingual character glossary
    retrieval-anchors.json # exact positive and negative anchor texts
    fixtures/              # authored, synthetic, redistributable examples
```

A module imports only the package modules that its row in the table of
`tests/test_module_layers.py` allows: its own layer or the ones below it,
and never in a cycle. The test reads every module, imports inside functions
included, and also checks that importing a module reads no file. Every
module may import `aimediator.__version__`. ADR
[0002](../decisions/0002-module-boundaries-and-entry-points.md) records the
decision. `run_store.code_manifest` and the legacy runner's
`shared_code_sha256` and `code-snapshot/` cover the top-level modules,
`design_briefs` and `diagnostics` included; the `collection/` subpackage is
outside run identities.

The research commands are package modules: `python3 -m aimediator.engine`,
`.legacy_review`, `.quality_scoring` and `.glossary_vectors`, which need
`pip install -e .` or `PYTHONPATH=src`. `scripts/` has no files at its top
level. The scripts in `scripts/collect/` and `scripts/experiments/` put the
checkout's `src/` first on `sys.path` and import `aimediator`; their first
docstring line never begins with "Compatibility entry point" (RULES.md G2).

Module contracts. The names below are each module's surface for other
modules, scripts and tests; a change to one updates every caller in the
package, scripts and tests together. Two rules hold for every module.
Serialization order is behavior: a dict literal, a schema's properties or a
list that reaches a request or an artifact keeps its order, and `sort_keys`
is neither added nor removed. The CLI maps exception types to exit codes, so
every path keeps the exception type it raises.

- `common`: `strict_json` (duplicate keys and non-finite numbers raise
  `ValueError`), `canonical` (sorted, compact UTF-8 JSON bytes), `sha`,
  `read`, `write` (indented, unsorted UTF-8 JSON, replaced atomically through
  a synced temporary file), `new_path`, `input_rows`, and `Failure(code,
  message)`, which carries the CLI exit code.
- `resources`: `asset_path(name='')` and `module_path(name)`. `glossary()`
  and `anchors()` load once per process, and callers never mutate the
  result; `retrieval` relies on exactly 10 positive and 10 negative anchors.
  `prompts(mode)` returns stage, then language, then text for `relevance`,
  `retrieval_review`, `extract` and `verify`, plus `quality` in `shadow` and
  `enforce`; in `enforce`, `extract` and `verify` get `'\n'` and the
  `quality-extract` or `quality-verify` appendix. The `relevance` and
  `retrieval_review` texts end with the topic list: after the asset, whose
  last line introduces it, one line `P<n>: <anchor text>` per positive and
  then `N<n>: <anchor text>` per negative anchor of
  `retrieval-anchors.json`, in file order, each ending with `'\n'`
  (pipeline upgrade step U2.4, UP-D07). `operations.prompts_for` is
  an alias. `workspace_root()` returns the checkout root when the package is
  imported from a checkout holding `RULES.md` and `pyproject.toml`, and the
  working directory otherwise, evaluated at call time.
- `schema`: `obj(properties)` (keys `type`, `additionalProperties`,
  `properties`, `required`) and `quality_obj(properties)` (keys `type`,
  `properties`, `required`, `additionalProperties`). They differ only in key
  order, which reaches the model through the request, so both are frozen and
  `tests/test_schema.py` pins each. Also `arr(items)`, `enum(values)`, the
  constants `STRING`, `NULLABLE_STRING`, `NULLABLE_NONEMPTY_STRING` and
  `BOOL`, and the validator `schema_errors(value, schema, path='$')`.
- `evidence`: `evidence_units`, `numeric_tokens`, `PARAMETER`, `CLAIM`
  (properties in the evidence-first order `evidence_ids`, `character`,
  `target`, `direction`, `recommendation`, `specificity`, `parameters`,
  `uncertain`; pipeline upgrade step U5.1, UP-D11),
  `character_reference(text='')` (new objects on every call, built from
  `resources.glossary()` and memoized by `text`; each call returns a new
  copy of the cached value, pipeline upgrade step U1.2), `character_terms(entry)` (canonical name, Chinese
  label, then the alias texts, unfiltered; callers filter),
  `character_candidates(text, reference)` and `ground_claim(claim, row,
  characters) -> (errors, enriched or None)`, whose span invariant raises

## 6. Configuration and input contracts

The generated config uses a versioned schema, rejects unknown keys, and contains:

- `schema_version = aimediator-config-v1`.
- Local Ollama endpoint, existing language/model routing, inference options,
  and finite connection/request timeouts.
- Embedding provider (`ollama` by default) and model configuration; configured
  service use is explicit and retains its lack of a locally verified weight digest.
- Quality mode, stop stage, and default policies/resources. Effective values
  resolve as packaged defaults < explicit config < explicit CLI overrides.
- Report scope `collection_sample`; glossary target-patch metadata is separate.
- `max_parallel_requests`, an integer from 1 to 8 (default 1), with the
  option `analyze --max-parallel-requests` (pipeline upgrade U3.2, UP-D08).
  `pipeline.ordered` runs independent units on a thread pool with at most
  that many in flight and commits their results in input order on the
  calling thread, so the trace, progress files and artifacts keep the serial
  order: one quality comment with its attempts, one audited claim, one
  relevance or retrieval-review batch (a retrieval-review batch with the
  single rechecks of its items), one relevance recheck, and one extraction
  batch with its split retries in serial order. `Runner` runs requests with
  the same identity one at a time; `operations.analyze` serializes the
  journal callback, `run-state.json` updates and progress lines with one
  lock. With 1, requests and writes are those of the serial code; above 1,
  fresh inference is not bitwise reproducible (the service batches parallel
  requests), while replay from the run journal stays exact. A configuration
  file without the key stays valid: resolution starts from the defaults.
  ADR [0004](../decisions/0004-bounded-concurrency-and-shared-cache.md)
  records the decision and the U3-L measurements: on the hosted API, 2
  parallel requests made the quality stage 1.25 times faster and 4 made it
  1.17 times faster, because the provider shares throughput.
- `cache_dir`, a path or `null` (default), with the option
  `analyze --cache-dir` (step U3.3, UP-D09): the shared cache of section 7.
  A relative path in a configuration file resolves against that file's
  directory, a CLI path against the invocation directory; the resolved
  absolute path is saved in `resolved-config.json` and enters the run
  identity. One cache directory is not shared by concurrent runs: two
  processes storing the same key at once can collide on the temporary file
  of `common.write` (ADR 0004).

Keep secrets out of JSON configuration, snapshots, request identities, and logs.
Configured embedding credentials come from named environment variables or an
explicit `--env-file` only; do not automatically open `.env` based on the current
directory. Local Ollama, demo, reporting, review, and evaluation do not need it.
Fix the current config helper so environment-only configuration does not require
an env file to exist. Record sanitized provider/endpoint/model identity, never
authorization headers or credential-bearing URLs. No cloud generation fallback.

Input is UTF-8 JSONL. Required fields are nonempty `record_id`, `text_original`,
and `language`; supported routed languages are `en` and `zh` (simplified Chinese
scope). `platform`, `source_id`, `source_url`, timestamps, patch/review metadata,
and original extra fields are retained when present. Missing metadata is unknown,
not inferred. Preserve existing larger collector records without dropping fields.
`record_id` is a global identifier within the file and maps to internal
`comment_id`; no regeneration of IDs is allowed.

Validate JSON strictly, reject duplicate keys, nonfinite values, wrong required
types, duplicate record IDs, and an empty dataset. Return line number and reason
without echoing an entire comment. Blank lines are ignored. Nonempty unsupported
language values receive coverage records and no model calls. If no record can
be routed, fail preflight with a clear message. Do not silently truncate long
comments; use the existing bounded processing/failure policy and expose failures.

Preserve original input bytes as `input-snapshot.jsonl` as well as parsed
`source-snapshot.json`, enabling exact dataset identity checks after relocation.
Use UTF-8 explicitly for all I/O. Quote offsets retain the existing unit-relative
versus source-relative conventions and are labeled in schemas; flattening them
into a report must include the appropriate source offset mapping.

```text
<run>/
  manifest.json                 # aimediator-run-v1, identity, provenance
  resolved-config.json          # sanitized, enough to resume
  input-snapshot.jsonl
  source-snapshot.json
  resource-snapshot/            # prompts, policies, glossary, anchors
  code-manifest.json            # relevant module bytes/digests, package version
  run-state.json                # atomic state and stage counters
  embeddings/<sha256>.json      # one record per embedded text (model, text, vector)
  requests/<stage>/<identity>/  # request/response/validation, partial attempts,
                                #   reuse-provenance.json for a shared-cache hit
  retrieval.json
  relevance.json
  full-pipeline-coverage.json
  validated-claims.json
  quarantined-claims.json
  balance-report.json           # preserve underlying engine schema/mode
  summary.json
  evidence-quality.json         # shadow/enforce only; other quality files retained
```

Existing source/prompt/policy snapshots can be preserved as aliases or migrated
with an explicit reader, rather than removing audit information. New manifests
include a product-schema version and the underlying engine/schema versions.

Run identity covers original input bytes, parsed source hashes, all active
prompts/resources/policies/schemas, topic anchors, relevant code, model digests,
the model service version, routing, inference options, quality mode, stop
stage, and embedding provider identity. The service version is the identity key
`service`, `{"ollama_version": <the version string of /api/version>}`, after
`models`; it is `null` when the service answers HTTP 404 (recorded as
unavailable), and fixture runs record `fixture-not-a-service` (pipeline upgrade
step U1.4, decision UP-D03). Store actual runtime/device options. Remote embedding model identity
has an explicit unverifiable-digest limitation. Times and output locations are
metadata, not inference-cache keys.

Use canonical serialized request content for request identity, including
model/digest, messages, schema, inference options, and attempt identity. Preserve
raw responses and rerun validation before using cached results. Same comment
ID or same model tag alone is insufficient. Cross-run reuse goes only through
the shared cache of `cache_dir` (section 6; pipeline upgrade step U3.3,
UP-D09), off by default: its key is the payload with `stream` false, the model
digest, the service version and the request context, never the run identity;
each reused response is marked by `requests/<stage>/<identity>/reuse-provenance.json`
and has `elapsed_seconds` 0. A run whose answers all come from the cache
reproduces the earlier run's request and artifact files exactly, apart from
elapsed times and timestamps (measured by U3-L, ADR 0004). Embedding records
are per text and shared under the embedding model digest (section 5,
`retrieval`). Historical exact-request replay remains a separate research
operation.

Lifecycle states: `created -> running -> completed|partial|interrupted|failed`.
Store current stage, requested stop stage, timestamps, failure reasons, and
completed request identities. A crashed `running` state is not completion;
resume reconciles actual persisted requests and coverage. Report export from an
incomplete run must be prominently labeled partial.

V1's supported operating system is Linux, matching the current environment;
macOS/Windows support is deferred until tested. Use atomic replacement for
structured artifacts and one advisory `fcntl.flock` writer lock per run. The OS
releases the lock after a crash. Do not silently delete another process's lock
based only on a PID. Completed
requests survive interruption; partial streams remain diagnostics and are never
accepted as valid JSON results. Retries retain distinct attempts and existing
bounded stage policies; never implement unbounded resume retries or accept
partial JSON to make a run finish.

Persist retry budgets per logical request across resumes. Resume continues
unfinished permitted attempts; it does not reset exhausted budgets or recycle
an attempt identity for a different response. If interrupted attempts consume
the budget, retain the interruption reason and leave the work partial. Repeated
resume after exhaustion must make no new calls and still report exit 5. A new
analysis directory is required for another bounded trial in V1.

On code/resource/model identity mismatch, exit 4 without modifying the run.
Resume reads `/api/version` after the model digests and refuses a different
service version, `null` included, with exit 4, "Service version differs from
saved run; start a new run", before any write.
The user must start a new run. Do not add `--force` to bypass identity checks.
Legacy runs are read-only inputs for supported report/review adapters; they
cannot be resumed by `aimediator analyze` under the new identity contract.

## 8. Coverage and report contract

Coverage is a per-input ledger, not a sum of counts from overlapping views.
Each input ID appears once with separate language, relevance, quality,
extraction, automatic-audit, and source-review states. Preserve legacy coverage
artifacts and add versioned product fields where needed.

Invariants:

- Input IDs equal coverage IDs exactly, including unsupported/unselected languages.
- Every admission either reaches the requested stop stage or has an explicit
  technical failure/pending state. Quality routing without extraction is normal.
- A structurally valid extraction with zero claims differs from generation failure.
- Every complete generated proposal has an automatic accepted/quarantined outcome.
- Every quality point has a route. A mixed comment can have several routes while
  remaining one coverage row. Requests/attempt counts are separate from comment counts.
- `status` and reports disclose unresolved technical work, genuine ambiguity,
  and unreviewed sources separately.

`report` writes `report.md` and `report.json` with a new export schema
`aimediator-report-v1`; it does not silently relabel the engine's `balance-report-v3`.
It includes run identity, mode, scope, source/publication ranges, language/platform
denominators, processing failures, unresolved cases, review provenance, evidence
links, and limitations. Missing source URLs fall back to local comment/evidence IDs.

Organize substantive content by verified character/system and topic, with
buff/nerf/keep/unclear shown together and original recommendation wording retained.
Use existing verified glossary concept IDs when already established. Otherwise
group only identical normalized literal targets within the same character;
unknown targets stay unresolved. Do not add semantic clustering or merge
synonyms across languages by similarity during packaging. Explain that literal
grouping can fragment equivalent topics.

Quality mode determines what can appear:

- `enforce`: separate general opinions, audited mechanism evidence, system
  feedback, exclusions, and review queue. Keep the existing eligibility checks.
- `shadow`: the formal view retains old extraction semantics; observed quality
  routing appears in a separate diagnostic section, never as enforced evidence.
- `off`: mark quality as unassessed. Retain all valid keep/unclear and system
  material already present in underlying artifacts, but do not infer missing
  concerns or fabricate quality classifications. Broader discovery requires a
  fresh enforce run, not report formatting.

Counts are unique comment-ID sets per topic/direction, with language/platform
breakdowns and clearly named denominators. Include union/overlap counts where
categories overlap; totals across topics are not people counts. Do not create a
global sentiment, confidence, or consensus percentage by averaging model claims.
Automatic, agent-reviewed, and human-reviewed figures remain distinct. Numeric
requests are only copied when explicitly source-supported; no new tuning values.

Reports use deterministic templates and escaped evidence text. Source text is
untrusted data, including instructions embedded in comments. Avoid executable
HTML or unsafe links; sanitize CSV cells against spreadsheet formula execution
in the worksheet while preserving canonical evidence in JSON.

## 9. Implementation order and acceptance gates

### P0: freeze the baseline and contracts

Read applicable project instructions, inspect current modules, and run the full
existing offline suite before editing. Record pre-existing failures honestly.
Create a new validation directory, not an old experiment directory. Confirm
the JSON contracts, exit codes, and legacy adapters from this design. Since
this workspace currently does not expose usable Git metadata to the design
session, use file hashes when revision identity is unavailable; do not assume
the next agent has a usable commit ID either.

Create `docs/plans/cli-implementation-status.md` during implementation. For each P0-P4
gate, record pending/in-progress/passed/blocked, the actual verification command,
result/artifact path, and remaining requirements. Update it at each completed
gate so another agent can continue from the last verified state. This design
remains the specification; the status document records execution and justified
deviations. Do not mark a milestone passed because code exists.

### P1: extract and install the engine

Add packaging, resource resolution, typed/validated configuration, pure-logic
modules, and injected transports. Move orchestration incrementally and retain
compatibility commands. Add manifest code/resource hashing independent of file
location. Gate: existing behavioral tests pass and a wheel imports outside the checkout.

### P2: complete operational commands

Implement init/doctor/analyze/status, explicit resume, state, locking, progress,
structured output, and exit handling. Gate: mocked fresh analysis, interruption,
compatible resume, and incompatible-resume rejection all preserve the coverage
and request-count invariants. Invalid inputs cause zero inference calls.

### P3: close the review/report workflow

Implement immutable review export/import, fingerprints, deterministic report
views, quality scoring adapter, and all-three-mode demo. Gate: an untouched
review template accepts nothing, correction cannot reuse a stale audit, and
the report never counts duplicate claims as extra supporting comments.

### P4: verify and document delivery

Run the full existing suite and meaningful product integration checks. Build
wheel/sdist; install the wheel into a clean environment outside the checkout,
with no `PYTHONPATH` assistance, and execute help, init, offline doctor, demo,
status, review export/import, and report. Verify installed resources and output
paths. The offline command path must make zero network calls even when unrelated
credentials exist in the environment. Confirm no raw community dataset, secret,
or private report is bundled.

Critical additional checks:

- Malformed/duplicate JSON, unsupported languages, empty input, wrong types,
  Unicode/emoji offsets, and input paths containing spaces.
- All quality/stop-stage combinations, stable off/shadow behavior, and enforce
  eligibility continuing through review/report.
- Missing service/model, explicit configured embedding, environment-only secrets,
  secret redaction, finite timeouts, and honest remote identity limitations.
- Interrupted streaming, technical retry exhaustion, repeated resume without
  duplicate counts, no overwrite, and competing writers.
- Changed input/prompt/policy/code/model/device options reject resume before mutation.
- Source/proposal/review hash mismatches and unknown legacy schema fail clearly.
- Topic conflicts, same-comment repeats, cross-group overlap, keep/unclear,
  unresolved identities, zero denominators, and partial-run report labels.

Do not write tests merely for Markdown wording or to mirror trivial parser
branches. Test persistence, evidence boundaries, resource portability, and user
workflows. Keep synthetic expectations separate from semantic quality claims.

If local inference services and the intended embedding provider are available,
run a small explicitly selected bilingual live diagnostic into a new directory.
Record exact inputs/configuration, raw requests/responses, runtime, failures,
and source-review observations. Do not automatically launch another 600-comment
experiment or download a missing model. If unavailable, finish offline delivery
and state exactly which live checks were not performed.

Follow the existing approximately 30-hour project budget as a planning reference,
not evidence that this remaining work fits it. Prioritize installability, the
analyze/resume path, immutable review, and traceable reports. Defer collectors,
glossary-management commands, interactive wizards, semantic topic merging, and
review revalidation before reducing evidence checks. Record actual work and any
remaining scope honestly; do not declare the whole V1 complete with missing commands.
